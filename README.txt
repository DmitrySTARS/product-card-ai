AI-ПОМОЩНИК ДЛЯ ПОДГОТОВКИ ТОВАРНЫХ ОПИСАНИЙ
============================================

Прототип сервиса, который по входным данным о контрольно-измерительном приборе
собирает черновик карточки товара для B2B-интернет-магазина: SEO-заголовок,
SEO-описание, список характеристик, поисковые запросы и блок для менеджера.

Главный принцип: сервис не выдумывает характеристики. Любой факт берётся
только из входных данных, отсутствующие параметры помечаются «данных нет», а
результат дополнительно проверяется автоматикой.


1. УСТАНОВКА И ЗАПУСК
---------------------

Требуется Python 3.10+. Внешних зависимостей нет, всё на стандартной библиотеке.

Проверка, что всё на месте (31 тест):

    cd product-card-ai
    python -m unittest discover -s tests


Запуск без API-ключа

    python -m product_card_ai.cli --input samples/products.json

По умолчанию работает провайдер offline: детерминированная сборка карточки
без обращения к LLM. Он нужен, чтобы прототип запускался по инструкции у любого
проверяющего и чтобы тесты были воспроизводимы.


Запуск с LLM

    copy .env.example .env      (Linux/macOS: cp .env.example .env)

В файле .env указать:

    PCA_PROVIDER=openai
    OPENAI_API_KEY=sk-...

и запустить:

    python -m product_card_ai.cli --input samples/products.json

Поддерживаются openai (Chat Completions, JSON-режим) и anthropic
(Messages API). Ключ читается только из переменных окружения или файла .env.
Файл .env добавлен в .gitignore, в коде ключей нет.


Веб-форма

    python -m product_card_ai.web

После запуска открыть в браузере http://127.0.0.1:8000

Одна страница: поле для JSON, выбор провайдера и формата, результат выводится
готовым к копированию блоком.


Параметры CLI

    Параметр          Назначение
    ----------------  --------------------------------------------------
    --input, -i       JSON-файл с товаром или списком товаров.
                      Если не указан, данные читаются со стандартного ввода.
    --provider        Провайдер: offline, openai или anthropic.
    --format, -f      Формат вывода: text (по умолчанию), markdown или json.
    --output, -o      Записать результат в файл вместо вывода на экран.
    --env             Путь к файлу с переменными окружения (по умолчанию .env).
    --strict          Завершиться с ненулевым кодом, если автопроверка
                      нашла замечания.

Коды выхода

    0   успех
    1   автопроверка нашла замечания (только при --strict)
    2   ошибка входных данных
    3   ошибка LLM
    4   ошибка конфигурации


2. ФОРМАТ ВХОДНЫХ ДАННЫХ
------------------------

Принимается один объект, массив объектов или объект вида {"products": [...]}.

Пример:

    {
      "name": "Манометр показывающий ДМ 02",
      "manufacturer": "Манотомь",
      "specs": {
        "диапазон измерений": "0–1,6 МПа",
        "класс точности": "1,5",
        "присоединение": "G1/2",
        "диаметр корпуса": "100 мм"
      },
      "description": "Прибор предназначен для измерения избыточного давления..."
    }

Обязательно только поле name. Отсутствие manufacturer, specs или description
не останавливает работу: эти пробелы попадают в раздел «Чего не хватает во
входных данных». Поле specs принимается и как объект, и как список вида
[{"label": ..., "value": ...}].


3. ПРИМЕР РЕЗУЛЬТАТА
--------------------

Готовые выгрузки по двум товарам лежат в папке examples:

    examples/output-both-products.txt    текст для контент-менеджера
    examples/output-both-products.json   JSON для интеграции

Исходные данные лежат в папке samples. Товары подобраны намеренно разными:

    1) Манометр ДМ 02 (Манотомь): полные данные, карточка получается цельной.
    2) Датчик давления СДВ-И: нет производителя, одна характеристика, короткое
       описание. Карточка всё равно собирается, но все пробелы явно перечислены.


4. АРХИТЕКТУРА
--------------

    product_card_ai/
      models.py       доменные структуры: ProductInput, ProductCard, отчёты
      validation.py   разбор входного JSON, поиск недостающих полей
      prompts.py      системный и пользовательский промпты
      providers.py    OpenAI, Anthropic, offline-провайдер
      pipeline.py     разбор ответа модели и автопроверка качества
      renderers.py    вывод в text / markdown / json
      config.py       чтение .env и переменных окружения
      cli.py          командный интерфейс
      web.py          локальная веб-форма

Поток данных:

    JSON -> validation -> prompts -> provider (LLM или offline) -> pipeline -> renderers

Отчёт о недостающих данных (InputReport) из validation передаётся напрямую
в pipeline и в renderers.

Разбор ответа и проверка качества вынесены в pipeline.py и работают одинаково
для любого провайдера: добавление новой модели не требует дублировать логику
контроля.


5. ПРОМПТЫ И ПРИНЯТЫЕ РЕШЕНИЯ
-----------------------------

Как устроен промпт

Системное сообщение задаёт роль контент-редактора и пять жёстких запретов:
не добавлять факты, писать «данных нет» вместо пропусков, не придумывать
стандарты (ГОСТ, IP, ATEX), не использовать числа вне входных данных, не писать
рекламные превосходные степени. Там же задана строгая JSON-схема ответа.

Пользовательское сообщение отдаёт данные тоже как JSON, отдельным блоком
перечисляет недостающие поля («не восстанавливай их по смыслу») и в конце
повторяет правило о числах. Повтор сделан намеренно: на длинном контексте
однократно упомянутое ограничение модели часто игнорируют.

Решения

1) Автопроверка вместо доверия промпту. Промпт не даёт гарантии. После
   генерации функция pipeline.check_quality извлекает все числовые значения из
   результата и сверяет их с числами во входных данных. Любое число, которого
   нет в источнике, попадает в unsupported_values и выводится предупреждением.
   Проверяются именно числа: формулировки модель имеет право перефразировать,
   значения нет.

2) Offline-провайдер. Без него прототип нельзя ни запустить без ключа, ни
   покрыть тестами детерминированно. Он собирает карточку перестановкой фактов
   из входных данных и принципиально не способен выдумать значение. Это
   нижняя граница качества, с которой сравнивается работа настоящей LLM.

3) Пробелы находит код, а не модель. Модуль validation.py сам определяет
   отсутствующие поля и отсутствующие типовые характеристики КИП, передаёт их
   в промпт и затем принудительно дописывает в missing_data. Если модель
   умолчала о пробеле, он всё равно окажется в результате.

4) Устойчивость к формату ответа. Для OpenAI включён JSON-режим, для
   Anthropic используется префилл ответа символом «{». Есть и запасной путь:
   если модель всё же обернула JSON в кодовый блок, обёртка снимается, а из
   текста вырезается первый сбалансированный JSON-объект.

5) Пометка «данных нет» нормализуется на входе. Если контент-менеджер уже
   вписал «данных нет», «n/a» или прочерк, это не считается значением.

6) Температура 0.2. Задача про точность, а не про вариативность.

7) Без внешних зависимостей. HTTP на urllib, веб на http.server, тесты
   на unittest. Критерий оценки включает простоту запуска, а каждая
   зависимость добавляет шаг установки.


6. ОГРАНИЧЕНИЯ
--------------

- Автопроверка ловит числа, но не выдуманный текст. Фраза «подходит для
  агрессивных сред» без чисел пройдёт проверку. Нужен семантический контроль
  или сверка утверждений с источником.

- Offline-провайдер даёт сухой текст. Он перечисляет факты, а не пишет
  маркетинговый текст. Это демонстрационный режим, не замена LLM.

- Длина SEO-описания не исправляется автоматически. Если модель вышла за
  800–1200 символов, выводится предупреждение, но повторная генерация не
  запускается.

- Нет кэша и пакетной обработки. Каждый товар отправляется отдельным
  запросом к LLM.

- Веб-форма рассчитана на локальный запуск одним человеком. Нет авторизации,
  CSRF-защиты и ограничения частоты запросов.

- Список типовых характеристик КИП задан в коде (validation.py) и покрывает
  приборы давления лучше, чем, например, расходомеры.

- Числа из названия товара считаются допустимыми, иначе «ДМ 02» давал бы
  ложное срабатывание. Теоретически это лазейка для модели.


7. ЧТО МОЖНО УЛУЧШИТЬ
---------------------

1) Автоматический повтор при замечаниях. Если автопроверка нашла выдуманное
   число или длину вне диапазона, отправить модели список замечаний и
   перегенерировать (1–2 попытки).

2) Проверка утверждений, а не только чисел. Вторым вызовом LLM сверять
   каждое предложение карточки с источником по принципу «подтверждается / нет».

3) Нормализация единиц. Сейчас «0–1,6 МПа» и «0-1.6 MPa» считаются разными
   строками; нормализация единиц измерения убрала бы ложные срабатывания.

4) Шаблоны по типам приборов. Свой список обязательных характеристик для
   манометров, расходомеров, датчиков температуры.

5) Пакетная обработка. Загрузка CSV/XLSX с каталогом и выгрузка результата
   в том же формате. Это то, что реально нужно контент-менеджеру.

6) Кэш по хешу входных данных, чтобы повторный прогон каталога не
   оплачивался заново.

7) Оценка качества промпта. Набор эталонных товаров с заведомо неполными
   данными и автотест «модель не добавила ни одного факта».
